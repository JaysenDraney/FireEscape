FireEscape: Plugin System Proposal

Draft for discussion. Target platform: Android TV and Google TV.

IdeaA small launcher core. Features arrive as plugins, including the ones shipped by default.
Plugin classes11 classes, grouped into 4 trust tiers.
Openness ruleNo capability is gated by payment or account. Spec, SDK and reference plugins are public.
First releaseCore plus 3 classes: Theme and layout, Wallpaper, Launch sources.

The core handles focus, layout, settings, and hosting plugins. Everything the user sees or does beyond that comes from a plugin class with a written contract. Sections 1 to 3 define what plugins can do. Section 4 defines the rules that keep the ecosystem open. Technology is limited to Appendix A.

How tiers are applied

  • A tier belongs to the class, not to the individual plugin. A plugin cannot claim a lower tier than its class.
  • The install screen shows the tier first, then the specific permissions the plugin asks for.
  • Review for the default index gets stricter as the tier rises: a schema check for Tier 0, up to a source review for Tier 3.
  • The capability table in section 3 shows what each class can and cannot do.

Finding something to watch: how classes 7 to 9 combine

  1. The user searches, or the home screen asks for a row. The launcher sends the request to every enabled catalog provider (7).
  2. Results are merged by shared ids and de-duplicated. If a recommendation provider (9) is enabled, it reorders them using the user's ratings, states why, and reports how confident it is. Section "Rows, priorities and schedules" below explains how that confidence is used.
  3. For the titles shown, availability resolvers (8) add where each one can be watched.
  4. The user picks a title and a way to watch. Only then does the launcher open the app or link.

Example: a title search returns matches from an online catalog and from a home media server, ordered by past ratings, with "on your server" and "rent or stream elsewhere" options attached.

Search is part of the catalog class. Any source that can list titles can also answer a query, so a separate search class would add nothing.

Rows, priorities and schedules: how a home screen is assembled

The launcher fills the rows of the active layout from a list of bindings. A binding connects a source to the home screen: a recommendation provider, a content rows plugin or a launch source. Nothing in this flow requires a plugin to be Tier 3.

  • Row slot. Declared by the layout: kind (cards, app tiles, hero banner), height, item size, scroll direction. A layout also declares how many rows it has. That number can be unlimited.
  • Binding. A source, a display label, a slot kind, a priority schedule, and an optional confidence floor. The same provider can appear in several bindings.
  • Priority schedule. A default priority plus rules such as "weekdays, 6:00 to 8:30 am: priority 1". A lower number means a higher priority. A rule can also switch a binding off. Priority is the only thing a schedule changes.
  • Row fill rule. At any moment the launcher orders bindings by their current priority and fills rows from the top. If there are more bindings than rows, the ones below the last row are not used. They are not asked for anything, so an unused provider receives no data. With an unlimited layout every binding gets a row.
  • Confidence. A provider reports how well its suggestions fit right now, from 0 to 1, for the row and optionally for each title. The launcher uses it in three ways only: it skips a row whose confidence is below the binding's floor, so the next binding moves up; it breaks ties between equal priorities; and it orders titles inside a row. Confidence never lets a lower priority binding outrank a higher one, so a provider cannot claim high confidence to push ahead.
  • Hero slot. A layout may declare a hero slot. It is bound like any row and shows the top title, or rotates the top few, from its provider. A hero needs a backdrop image and a short tagline for each title, and the tagline is the provider's reason text. A provider declares which slot kinds it can serve. If it cannot supply a backdrop, it is not offered for a hero slot.
  • Asking order. The launcher asks bindings in priority order and stops when the rows are full. A skipped row is replaced by the next binding. Rows far below the screen can be asked lazily as the user scrolls.
  • Manual override. A remote button opens a picker that pins a binding into a row until the next schedule change.
  • Schedules, priorities and confidence floors are launcher data. A plugin never sees the schedule. It is asked for a row only when its turn comes.
  • A household writes one recommendation provider per purpose, for example school-day picks for a child and evening picks for two adults. The launcher has no notion of people. Any per-person tuning lives inside the provider.
  • Ratings stay in the launcher's shared store. A provider that needs its own data keeps it itself, within the data level the user approved (see External services and trusted publishers in section 4).
  • The launcher cannot tell who is watching. A schedule by the clock is a guess, which is why the manual override exists.

Setting things up with the remote

All configuration can be done with the remote that comes with the TV.

  • Baseline input. D-pad, Select, long-press Select and Back. Android TV guidance expects apps to work with those buttons, so nothing in setup depends on anything else.
  • Editing a row. Long-press a row to open a menu: change source, edit priorities, set the confidence floor, move, hide.
  • Priority editor. A list of time windows. Up and down change a value, left and right move between fields, and Select toggles day chips.
  • Time scrubber. Slide a time of day and see which bindings take the rows at that moment. It shows the same picture as the figure above, for your own setup.
  • Extra buttons are optional. Menu, color keys, brand buttons and voice keys differ by remote and firmware, and some never reach an app. A "press a button" step records whichever key the TV exposes, and nothing depends on it. A "Now showing" chip on screen replaces a missing override button.
  • Plugins never receive remote keys. Key handling stays in the core.
  • Setup is data. Bindings, priorities and floors export and import as a file, so labels and long lists can be edited on a PC or phone.

2Class details

Each class has a written contract: what the launcher sends, what the plugin returns, and what it cannot do. The diagram highlights the screen area the class controls.

1

Theme and layout

Tier 0 · no code

Changes how the home screen looks and how it is arranged.

Launcher sends
Nothing. The launcher reads the pack.
Plugin provides
A pack: color and type tokens, corner radius, a focus effect from a fixed set, a layout template (rows, grid, gallery, carousel), icon mappings by package name. A template lists its row slots: for each, a kind (cards, app tiles, hero banner), height, item size and scroll direction. It also says how many rows it has, which may be unlimited.
Applies
When the user selects the pack.
Cannot
Run code, use the network, or read data.

Examples: gallery layout with one large row, high-contrast pack, large-text pack, icon pack that replaces app icons.

2

Wallpaper providers

Tier 1

Supplies background images or video behind the home screen.

Launcher sends
Screen size and idle or active state. Optionally the focused tile's package name, off unless the user grants "focus context".
Plugin returns
An ordered list of media items: image or video source (URL or file), title, credit, display duration.
Updates
On a timer, on focus change, or on idle change, as the plugin declares.
Cannot
See the app list, start anything, or draw outside the background layer.

Examples: Apple Aerials video list, public-domain museum art, a local photo folder, an album from a home server, now-playing artwork, generated gradients.

3

Widgets

Tier 1

Shows small pieces of live information in header slots.

Launcher sends
Slot size, theme tokens, a once-per-minute tick.
Plugin returns
A small declarative layout (text, icons, bars) or a surface of the slot's size.
Updates
Plugin pushes updates, rate-limited by the host.
Cannot
Take focus unless declared focusable, start anything, or exceed its slot.

Examples: clock and date, weather, next calendar event, Wi-Fi and VPN status, home sensor readings, now playing.

4

Idle providers

Tier 1

Replaces the screen with its own content while the TV is idle.

Launcher sends
Idle start and stop, screen size, power state.
Plugin returns
A full-screen surface or a media list, shown only while idle.
Updates
While idle.
Cannot
Intercept keys. Any key press ends it and returns to the home screen.

Examples: Aerials footage, rotating art, ambient clock, photo frame.

5

Content rows

Tier 2

Fills rows with cards. Selecting a card opens something.

Launcher sends
Row slot size, locale, which card the user selected.
Plugin returns
Rows of cards: title, image, subtitle, and a target to open on selection.
Updates
On a timer or when the launcher becomes visible.
Cannot
Open anything itself. The launcher opens the target after the user selects the card.

Examples: continue watching from a media server, news headlines (RSS), photo albums, upcoming fixtures, saved links.

6

Launch sources

Tier 2

Supplies the things a user can open. The installed-apps list is itself one of these plugins.

Launcher sends
Nothing by default. May request the installed-app list with a grant.
Plugin returns
Launchable targets: id, label, icon, and how to open it (app intent, HDMI input, URL, remote host).
Updates
On install or removal events, or on a timer.
Cannot
Open a target by itself. Users sort, group and hide targets in the launcher.

Examples: installed apps, HDMI and tuner inputs, web shortcuts, game-streaming hosts, smart-home scenes, network shares.

7

Catalog providers

Tier 2

Supplies titles and metadata for browsing and for search.

Launcher sends
A browse request or a search query, and the locale. Nothing about what is installed or watched.
Plugin returns
Titles: stable ids (TMDB, IMDb, or its own), type, year, artwork, ratings, genres, and any credit text its source requires. May accept ratings back if the user approves.
Updates
On request, within the caching limits of its source.
Cannot
See installed apps or watch history, or open anything.

Examples: TMDB lists and search, lists from a list-keeping service, a Jellyfin or Plex library, an RSS feed, a folder of local files.

Search. The launcher sends each query to every enabled catalog, merges results by shared ids, and removes duplicates. Plugins that need an API key use the user's own key.
8

Availability resolvers

Tier 2

Answers where a title can be watched and how to open it.

Launcher sends
A title with its external ids, the services the user listed in settings, and the region.
Plugin returns
Ways to watch: service, app target or deep link, and whether it is included, a rental or a purchase, when known.
Updates
On request, cached.
Cannot
Open anything, or know which services the user pays for beyond the list the user entered.

Examples: TMDB watch-provider data (sourced from JustWatch, credit required, no full deep links), per-app deep-link templates kept in a public repository, Android TV Watch Next entries, the user's own media server.

9

Recommendation providers

Tier 2

Ranks and proposes titles from candidates, ratings and history, and says why.

Launcher sends
A candidate pool, and the slot kind and size it is filling. Ratings or watch history only at the data level the user approved for this provider.
Plugin returns
A ranked list with a reason for each title (for example "because you rated a similar title highly"), and a confidence from 0 to 1 for the list and optionally for each title. For a hero slot, titles can carry a backdrop image and a short tagline. The plugin declares which slot kinds it can serve.
Updates
On request, when ratings change, and when its binding comes up for a row on the schedule.
Cannot
Open anything, or receive more data than the level the user approved. A provider that uses an external service also needs a trusted publisher (section 4).

Examples: a rule set ("unwatched, rated 4 or higher, under two hours"), an on-device model, a community list ranked by your ratings, a recommendation provider running on your own server.

Ratings. The launcher owns the rating buttons and stores ratings on the device. Recommendation providers read them. A catalog plugin may write ratings back to a service only if the user approves it for that plugin. A provider can also keep its own data if it needs tuning for one household member or one time of day. Providers are local unless they declare an external service. Priority and confidence are set in the binding, not by the provider.
10

Automation

Tier 3

Reacts to events and performs actions without the user pressing anything.

Launcher sends
Events: boot, wake, idle, input change, button press, app opened or closed, network change, time.
Plugin returns
Actions: open a target, switch profile, change wallpaper set, remap a button, show a notice. Privileged actions need a system grant.
Updates
Event driven.
Cannot
Act invisibly. Every automation is listed in settings and each action is logged.

Examples: open a chosen app at boot, switch to an evening profile at 7 pm, long-press for an input picker, return home after 10 minutes in an app.

11

Profiles and policy

Tier 3

Decides what each profile can see, and when.

Launcher sends
Active profile, list of targets, current time.
Plugin returns
Rules: which targets and rows are visible per profile, PIN gates, schedules, daily time budgets.
Updates
On profile switch and on schedule.
Cannot
Act as a security boundary. See the note below.
Limit. A launcher can hide and lock what its own screen shows. It cannot stop someone from opening Settings, installing a different launcher, or using ADB. For enforcement, use platform controls such as Google TV kids profiles. This class is for presentation and convenience on top of them.

Examples: kids profile with an allow-list, bedtime lock, per-app PIN, guest mode.

Defaults: every capability is denied. A plugin declares what it needs, and the launcher lists those requests at install time in plain language. The launcher controls what it hands a plugin: the installed-app list, ratings, history, the schedule. It can withdraw those later. It cannot take back a network permission that an installed plugin already has, and it cannot see what a plugin sends. For network use the declaration is a disclosure, and trust in the publisher is the control. A system grant means a permission Android only allows through ADB or a system setting, which the user has to apply deliberately.

Combination rule. A provider that can reach the network never receives watch history. It receives ratings only if its publisher is trusted and the user chooses that data level by name. Recommendation providers are local by default. See External services and trusted publishers in section 4.

External services and trusted publishers

A recommendation provider can use an external service, for example a model run by its publisher. The provider then handles the user's ratings on someone else's server. This is the riskiest use of a Tier 2 class, so it has its own rules.

What the launcher can and cannot enforce.

  • Can: decide whether to ask a provider at all, and what data to hand over.
  • Cannot: see or block what a plugin does with data it has received, or which servers it contacts. Android lets an app with the network permission reach any host. Declared hosts are disclosure, not enforcement.

The real control is whom the user trusts. The rules below limit how much a trusted publisher is handed.

Data levelWhat the provider receivesAllowed for
1 Candidate poolTitles to rank, and the slot it is filling. No personal data.Any provider. The default for external ones.
2 Plus ratingsThe user's ratings of titles.Local providers. External providers only from a trusted publisher, chosen by name.
3 Plus watch historyWhat was watched and when.Local providers only.
  • Local by default. A provider with no external service declaration is local. External providers are marked "External service" wherever they appear.
  • Trusted publishers. An external provider installs only if its publisher is on the user's trusted list. A publisher is identified by a signing-key fingerprint, a name and a source URL. Adding one takes a deliberate screen that names the publisher and what it could receive. Removing a publisher disables its providers.
  • Disclosure at install. The declared hosts and a link to the publisher's privacy statement are shown. The launcher does not verify either.
  • Data log. Settings lists each time data was handed to a provider: which provider, which data level, and when.
  • Unused means untouched. A binding that falls below the last row (see section 1) is not asked, so it receives nothing.
  • Your own service. If you run the service yourself, you are the publisher. You add your own key to the trusted list.
  • Default index. External providers are listed only with a source link and a privacy statement, and flagged as external. Other indexes can list anything.

Authoring path

  • A template repository for each class, building out of the box.
  • A mock host app to run and test a plugin without a TV.
  • Per-class docs generated from the same schemas the launcher uses.

Limits of openness

  • Open source does not prevent a malicious plugin. Permissions, tiers and review for the default index reduce the risk. They do not remove it.
  • The launcher cannot stop a user from adding a third-party index that lists plugins we would exclude.
  • Profiles and policy plugins are not a security boundary (see class 11).

5Phasing and scope

PhaseDeliversReason
0Core, plugin host, permission screens, one default indexEverything else depends on it.
1Theme and layout (with row slots), Wallpaper providers, Launch sourcesLaunch sources are needed for the launcher to be usable (installed apps are one). Theme and Wallpaper are the lowest-risk visible features.
2Widgets, Idle providers, Content rows, Catalog providers, Availability resolvers, local Recommendation providers, row bindings with priority schedules and confidenceLocal providers need no trust machinery beyond data levels. Bindings with priorities are the core of the home screen. Catalogs and availability give search and "where to watch".
3Recommendation providers that use an external service, Automation, Profiles and policyExternal providers need the trusted-publisher list, data levels and the data log. Automation and Profiles are the highest privilege. All need real use of earlier phases first.

Out of scope

  • Replacing the launcher core or its focus engine through a plugin.
  • Building full applications inside the launcher. Plugins hand off to apps.
  • Playing protected streaming content. That stays in the streaming apps.
  • Ad or sponsored-recommendation insertion.
  • Scheduled lineups or linear channels, meaning deciding which title plays at what time. Rows can appear on a schedule, but nothing here schedules playback.
  • Syncing settings across devices (possible later, not designed here).

AAppendix: Technology

Brief, and subject to change. None of the proposal above depends on the specifics here.

  • Platform: Android TV and Google TV. Kotlin with Jetpack Compose for TV for the launcher UI.
  • Plugin transport (Tiers 1 to 3): separate APKs. Each exposes a bound service with a versioned AIDL interface per class. The launcher finds plugins by a per-class intent action.
  • Declarative packs (Tier 0): JSON validated against JSON Schema, with image assets. No executable content.
  • Video: the launcher plays video with Media3. Plugins return sources, not decoders.
  • Permissions: capabilities declared in plugin metadata. The launcher controls the data it passes across the plugin interface. Android grants network access at install, so the launcher cannot revoke it or inspect traffic. System-level actions rely on ADB-granted permissions, as Android requires.
  • Trusted publishers: stored as signing-certificate digests. Updates to a plugin must match the key it was installed with.
  • Row resolution: bindings are asked in priority order until rows are full, with results cached per binding for a time-to-live the provider suggests.
  • Remote input: Compose for TV key handling for D-pad, Select, long-press Select and Back. Optional extra keys are learned by logging the key codes the device delivers.
  • Distribution: signed JSON index. Updates must match the installed plugin's signing key.
  • Testing: conformance tests per class, run against a mock host.

<service android:name=".AerialsWallpaper" android:exported="true">

BAppendix: Evidence and gaps

Checked while preparing this:

  • One popular closed launcher treats third-party wallpaper plugins as a paid feature, per the README of a plugin built for it.
  • The Aerials wallpaper plugin accepts custom JSON or M3U media lists, which is the model the Wallpaper class follows.
  • One open-source Compose-for-TV launcher reviewed (Homie) has no plugin hooks, no content provider and no service binding in its code.
  • TMDB's watch-provider data comes from JustWatch and requires crediting it. TMDB states it does not offer full deep links. Its API is free for non-commercial use with attribution.
  • Fire TV and Apple TV search work through catalog and availability feeds that streaming services supply to the platform owner, per Amazon's and Apple's partner documentation.
  • Android TV guidance expects apps to work with a remote that has only up, down, left, right, Select, Back and Home. One open-source launcher's notes report that an accessibility key filter received extra remote buttons on one TV model and not on another.
  • Android TV's TV provider is how apps publish Watch Next entries. One launcher's documentation says reading them needs the READ_TV_LISTINGS permission, which can be granted from a shell. Not tested on a device.

Not checked:

  • The wire protocol of that closed launcher's plugin interface, and the license of its sample plugin project.
  • How far Android TV lets a launcher enforce restrictions beyond its own screen.
  • Whether any mechanism lets a launcher limit another app's network access. The design assumes none, which is why it relies on trusted publishers.
  • Which extra buttons the onn. 4K Plus remote delivers to an app. This needs a test on the device.
  • Whether Google voice search can be reached from a third-party launcher, and how many streaming apps support deep links to specific titles.
  • Plugin support in the other open-source launchers. None advertised it in the pages read, which is not proof that none have it.
